01　产品概述

一件具体的小事，为什么需要整理

下面这条通知，是很多社区最常见的写法（本项目编写的演示样例，不是真实社区公告）：

各位居民：为帮助老年居民掌握智能手机常用功能，社区服务中心将开展“手机使用指导”活动。
时间：2026年10月26日9:00—11:00　　地点：社区服务中心二楼活动室
报名方式：请于2026年10月25日17:00前到社区服务中心一楼服务台报名，名额有限。
说明：本次活动仅限已报名居民参加，请携带本人手机。

八十几个字里有四组关键信息，而且互相“长得像”：

容易读错的地方为什么
两个时间25 日 17:00 是报名截止，26 日 9:00 是活动开始。错当成“25 日去参加”，就白跑一趟。
两处地点报名在一楼服务台，活动在二楼活动室。合并成一个“社区服务中心”，到了还得再问。
一个限制“仅限已报名居民参加”决定了要不要提前跑一趟；漏掉这句，当天可能进不去。
一份材料只写了“本人手机”。实际准备时，人容易顺手再带身份证、医保卡——通知并没有要求。

明白办做的事：把这条通知整理成一张卡——先说这条通知要办什么，再把两个时间、两处地点、限制条件、要带的东西分条列出，每一条都能点开看到通知里的原句；通知没写的，就写“通知未说明”，不替它补。

目标用户：主要操作人是家人或社区志愿者，受益者是长辈。长辈不必自己复制粘贴长段文字；但卡片写得中性、可独立阅读，长辈拿到就能自己看明白，去不去、怎么办仍由本人决定。

02　目标用户与协作流程

两步由人做，一步由 AI，一步由程序把关

谁在做什么

角色具体动作为什么必须由人来做
家人 / 志愿者复制通知文字、点“整理成行动卡”、逐项对照原文、转发给长辈只有人知道这条通知和自家情况的关系，也由人决定要不要去
AI（大语言模型）读懂任意写法、拆出事实、判断缺失与冲突、改写成白话通知措辞千变万化，规则与模板覆盖不了
程序（确定性校验）检查结构、字段、状态取值、每条引文是否真的出现在原文里只有机械检查才能每次都一样地执行，不依赖模型心情
长辈看卡片、决定去不去、按卡准备——

适老化不是“把字放大”

  • 正文 20px、行高 1.75；关键事实 22px；按钮最小 56px，复选框 32px（整行可点）。
  • 状态不只靠颜色：原文写明 ✓ 实线、通知未说明 — 虚线、说得含糊 ? 点线、前后不一致 ! 双线。
  • 360 / 390 / 768 / 1280 四档视口实测无横向滚动；键盘 Tab 焦点可见；配色对比度全部 ≥4.5:1。
  • 手机上先给输入框和主按钮，插画放在按钮之后——360×780 下主按钮顶部在 694px，首屏可见。

03　核心功能

四项功能，都在真实界面里

编号功能实现要点
F1通知输入粘贴文字，上限 5000 字；空白与超长都有明确提示且不静默截断；三条虚构演示样例一键填入
F2事实整理一句话说清“要办什么”，再按 谁适用 / 何时何地 / 准备什么 / 下一步 / 还要确认 分条
F3原文核对每个事实项标注四态之一，可展开“对照通知原文”；时间与地点分别挂载，报名地点与活动地点不合并
F4准备与复制准备清单可勾选；一键复制整张卡，复制文本按当前勾选输出 [x]/[ ]，并声明“不是报名凭证”
界面上的两处关键设计：①冲突或含糊时，结论卡下方立刻出现确认横幅（红框双线 + “!”），不折到页面底部；②“准备什么”与“下一步”分开两节，勾选只记准备状态，不写“已报名”。

05　AI 的角色与价值

模型负责理解，程序负责核对，人负责决定

环节谁做边界
读懂通知大语言模型：处理口语、简称、模糊表述、长句套长句模型不判断资格、不做医疗法律建议
拆出事实模型：按固定 JSON 输出对象、时间（含用途与地点）、准备、下一步、待确认必须给逐字原文摘录
机械校验程序：字段类型、status 取值、missing 不得填值、每条引文必须能在原文中逐字找到、required 必须有依据校验不过 → 重试 1 次 → 仍不过则不出卡
判断去不去人：家人核对、长辈决定产品不代办、不报名

为什么这一步不能只靠提示词

提示词能约束模型“不要编”，但无法证明它没编。所以产品在模型之后加了一层可判定的检查：把模型给出的每条引文拿去原文里找，找不到就判失败。这层检查是机械的、每次都一样，不依赖模型这次是否听话。

必须说清的限制：引文能在原文找到，不等于理解一定正确。程序只能发现“引文对不上”“结构不完整”“标了要求却没有依据”，发现不了“引文真实但把意思读反了”。所以结果页始终提示以通知原文和社区说法为准，产品里没有任何“绝不出错”“保证不编造”的字样。

运行时的模型服务（如实记录）

项目实际情况
接入方式WorkBuddy 云服务托管的免密钥大模型通道；浏览器直连数据面，服务端按 Origin 校验，前端不保存长期密钥
实际模型deepseek-v4.1-flash，由模型列表接口读取后选用；页脚显示本次实际使用的模型名
参数流式输出、temperature 0.1、单次超时 45 秒、失败最多重试 1 次（网络瞬断也重试 1 次）
无法确认上游提供方的机房与部署形态由平台托管，本项目无法核实，故不作声明

06　技术实现思路

六步链路，只有一处外部依赖

技术选型

  • 前端：原生 HTML/CSS/JS，无框架、无构建步骤
  • 模型接入：WorkBuddy 云服务 SDK（浏览器 CDN 版）
  • 校验：自研 validate.js（结构与引文回溯）
  • 托管：静态站点，单端口 HTTP 服务

关键实现

  • 提示词只存一份，运行时读取 prompts/system-prompt.txt
  • 请求序号丢弃过期响应；加载中禁用按钮
  • 全部文本走 textContent，不拼 innerHTML
  • 剪贴板三级降级，最后给手动全选框

输出契约（节选）

document_status · summary · audience · times[{purpose,value,status,evidence,place}] · location · preparation · actions[{type,value,evidence}] · questions · warnings
status 仅取 stated / missing / unclear / conflict；missing 时 value 必须为 null、evidence 必须为空。required 必须有能回溯到原文的引文，否则整张卡不出。

还没做到的

  • 未开展目标用户试用。没有长辈或志愿者使用本版本的记录，因此不提供任何效果、满意度、节省时间的数据。

08　应用价值与下一步

从一张卡开始，先做小范围验证

它现在能解决什么

场景产品做的事
家人替长辈读通知先整理成卡，核对原文后转发；避免口头转述时漏掉楼层、截止时间、限制条件
社区志愿者协助登记批量面对写法各异的通知时，快速得到统一格式的事实清单，缺口一眼看出
长辈自己复查卡片可独立阅读，能反复看“要带什么”“几点在哪”，不必再打电话问

下一步怎么验证（不承诺结果）

  • 配对试用：3—5 组“家人 + 长辈”，用两条难度相近的通知，一条直接读、一条用产品看，交叉顺序；记录找到正确时间地点的比例、是否需要协助、卡住的位置。模板见 15_用户试用材料。
  • 社区侧小范围：请 1—2 位社区工作者用自己的通知试整理，看“未说明/冲突”提示是否帮到他们。
  • 真机测试：在长辈实际使用的手机上验证字号、触控与微信内置浏览器打开。
  • 输入形式：先做截图识别（OCR），再做卡片朗读——两项目前都只是计划，产品里还没有入口。
商业化与合作：目前没有任何商业合作、政府采购或社区落地。可能的路径（社区养老服务、社会组织工具）都只是待验证设想，不作为既成事实。
