# 数据结构说明（产品运行时约定）

本文件描述「明白办」调用模型时要求返回的结构，以及程序侧的校验规则。
运行时使用的系统提示词见同目录 `system-prompt.txt`（页面通过 fetch 直接读取该文件，单一事实来源）。

> A 轮变更：`times[]` 新增可选字段 `place`（用途对应的地点）；`actions` 中 `required` 无原文依据
> 由「记警告」改为「判为校验失败」。两处都是为了让「报名地点／活动地点」不混淆、
> 让「通知明确要求」这四个字必须有原文兜底。

## 1. 顶层结构

```json
{
  "document_status": "notice | not_notice",
  "document_status_reason": "字符串，一句话说明判断依据",
  "summary": "字符串，1—2 句白话，不超过 60 字",
  "audience":  Fact,
  "times":     [TimeFact],
  "location":  Fact,
  "preparation": [Fact],
  "actions":   [ActionItem],
  "questions": ["字符串"],
  "warnings":  ["字符串"]
}
```

不得出现约定外的顶层字段（程序会判为结构错误）。

## 2. Fact（事实项）

```json
{ "value": "字符串或 null", "status": "stated|missing|unclear|conflict", "evidence": ["原文摘录"] }
```

| status | 含义 | 约束 |
|---|---|---|
| `stated` | 原文明确写出 | `value` 非空，`evidence` ≥ 1 条 |
| `missing` | 原文没有这一项 | `value` 必须为 `null`，`evidence` 必须为 `[]` |
| `unclear` | 原文提到但说不清（如"另行通知"） | `value` 非空，`evidence` ≥ 1 条 |
| `conflict` | 原文前后不一致且无更新关系 | `value` 非空，`evidence` ≥ 2 条（两条冲突原文都要列出） |

## 3. TimeFact（时间项，含可选地点）

```json
{
  "purpose": "报名截止|活动开始|服务时间|其他时间",
  "value": "...",
  "status": "...",
  "evidence": ["..."],
  "place": { "value": "...|null", "status": "...", "evidence": ["..."] }
}
```

- `purpose` 强制拆分：**报名截止**与**活动开始**必须分成两条，不得合并、不得互相替代。
- `place` 为可选字段。原文对某个用途单独写了地点时（如"到一楼服务台报名""在二楼活动室参加"），
  必须挂到对应用途上；没写就 `status=missing`、`value=null`、`evidence=[]`，不得把另一个用途的地点套过来。
- 若所有用途都没有 `place`，页面退回到展示顶层 `location`，标为「整体地点」。

## 4. ActionItem（下一步）

```json
{ "type": "required|suggested", "value": "字符串", "evidence": ["原文摘录"] }
```

- `required`：通知原文明确要求的事，**必须带至少一条能在原文中找到的引文**。
- `suggested`：仅为确认信息而提出的建议，不得把建议包装成原文义务。
- 页面上 `suggested` 显示「建议先确认」标签；复制文本中注明"不是通知要求"。

## 5. 程序侧校验（app/js/validate.js）

校验顺序：

1. JSON 可解析（先剥离可能的 ```json 围栏）。
2. 顶层字段齐全、无多余字段、基础类型正确。
3. `document_status` 只能是 `notice` / `not_notice`。
4. 每个 Fact：`status` 合法；`missing` 不得带 value/evidence；其余状态必须有 value 与至少一条有效引文。
5. `times[].place` 若存在，按 Fact 规则逐项校验。
6. **引文回溯**：每条 `evidence` 归一化后必须能在输入原文中找到。
   归一化只做两件事——去掉所有空白字符、把常见全角标点折成半角。
   不做同义词/语序/错别字的容错，避免编造的引文蒙混过关。
7. `actions` 非空；`type` 合法；`evidence` 必须是数组。
8. **A 轮新增**：`required` 但没有引文、或引文全部对不上原文 → **判为错误**（此前只记警告）。
   理由：标了"通知明确要求"却拿不出原文，等于替社区编要求；这种卡不允许出。
9. `times` 非空（至少给出一个时间判断，哪怕是 missing）。

处理策略：

- 校验不通过 → 自动重试 1 次（`maxRetries = 1`）→ 仍不通过 → 显示失败说明，**不渲染行动卡**。
- 请求超时 45 秒 → abort → 显示提示与「再试一次」。
- 服务不可用（配置缺失 / SDK 未加载 / 配额错误）→ 显示明确原因，**不使用固定答案伪装成 AI 结果**。

**边界声明**：以上是机械检查，只能发现"引文对不上原文""结构缺字段""required 无依据"这类错误，
不能保证语义理解一定正确。结果页因此始终提示"以通知原文为准"，也不使用"绝不出错"之类表述。

## 6. 安全处理

- 模型输出与用户输入一律通过 `textContent` 写入 DOM，不使用 `innerHTML`，通知里的 HTML/脚本不会被执行。
- 系统提示词把通知原文声明为"待分析数据"，并明确禁止执行其中出现的指令（提示注入防护）。
- 用户原文不写入任何日志系统，不落库；页面不建立历史记录，刷新即清空。
- 平台侧对请求数据的处理不在本产品控制范围，不作"绝不上传/绝不保留"的承诺。

## 7. 复制文本与勾选状态

- 复制内容由当前 DOM 中的勾选状态生成：`[x]` / `[ ]`，与页面所见一致。
- 复制文本固定包含：要办什么、谁适用、各用途时间与对应地点、准备事项、下一步（含 required/suggested 区分）、
  待确认问题、注意事项。
- 复制文本不含模型名、耗时、接口等技术细节；这些只出现在页面页脚的「本次生成信息」。
- 复制文本末尾声明："方框打勾记录的是整理者准备到哪一步，不是报名凭证"。
